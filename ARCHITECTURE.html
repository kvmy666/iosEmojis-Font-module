01

The Big Picture

SF Pro
replaces system Latin font
SF Arabic
replaces all Arabic fonts
🍎 Emoji
replaces NotoColorEmoji.ttf

The core idea is simple: Android reads font files from /system/fonts/ at boot. If you control what files are there, you control what every app renders. The problem is that /system is a read-only partition (erofs). We solve this with KernelSU's magic-mount — we project a shadow over the real partition without ever touching it.

Key insight

We never modify the system partition. We never flash anything permanent. KernelSU overlays our font files on top of the real /system/fonts/ using a Linux kernel feature called OverlayFS. Remove the module, and everything reverts instantly.

02

How Android Loads Fonts

The config file chain

Android's text engine (Minikin) reads font configuration from several XML files. On Android 16 the chain looks like this:

font_fallback.xml
The REAL config — Minikin reads this first and uses it for all font resolution
Root-only readable. References exact filenames like NotoColorEmoji.ttf. This is why our Apple emoji must be named exactly that.
fonts_customization.xml
OEM/module overrides — replaces named families like "sans-serif"
We write this file at boot to replace sans-serif with SF Pro — works universally across all OEMs.
fonts.xml
DEPRECATED — kept only for apps that parse it directly, not for Minikin
Lesson we learned the hard way

fonts.xml literally says "DEPRECATED: This XML file is no longer a source of the font files installed in the system." We spent time injecting emoji into fonts.xml — which had zero effect because Minikin wasn't reading it for that.

How Minikin picks an emoji font

When you type 😀, Minikin does this:

1. Look up Unicode codepoint → U+1F600
2. Find a font family with lang="und-Zsye" (emoji script) in font_fallback.xml
3. First listed: → NotoColorEmoji.ttf
4. Search for that file in /system/fonts/
5. Load it and render the glyph

Step 4 is where we win: our Apple emoji IS at /system/fonts/NotoColorEmoji.ttf

Color emoji formats compared

FormatTableUsed bySizeType
CBDT/CBLC CBDT Our Apple emoji repack ~111 MB Color bitmap (PNG strips)
COLRv0 COLR Stock Android 16 Noto ~2.8 MB Color vector (compact)
COLRv1 COLR Newest emoji fonts ~3–5 MB Color vector (gradient support)
sbix sbix Apple native (macOS/iOS) ~50 MB Color bitmap (PNG per glyph)
03

The Boot Sequence

Timing matters enormously. We have a very specific window to run our code — after /data is mounted but before Zygote starts.

Power on → Bootloader → Kernel
Kernel mounts partitions: /, /system (read-only erofs), /data
KernelSU hooks in (kernel-level)
OverlayFS activated — our module files are projected over /system/fonts/
🟢 post-fs-data phase ← OUR CODE RUNS HERE
post-fs-data.sh executes as root
✓ /data is mounted — we can read config.json
✓ /system is overlaid — our fonts are visible
✓ Zygote has NOT started — fonts haven't been loaded yet
🔴 Zygote starts ← point of no return
Reads font_fallback.xml + fonts_customization.xml, loads fonts into memory cache
All apps fork from Zygote and inherit its font cache. If we ran code here we'd be too late.
system_server → Boot completed
service.sh runs (writes perf.log, then exits — no daemon)
User unlocks screen — sees Apple fonts 🍎
04

KernelSU Magic-Mount

KernelSU uses OverlayFS — a Linux kernel feature — to project our module's files over /system. The real partition is never touched.

Real /system/fonts/
Roboto.ttf 4.8 MB
NotoColorEmoji.ttf 2.8 MB
NotoSans-Regular.ttf ~12 MB
NotoNaskhArabic-*.ttf various
→
After magic-mount
Roboto.ttf 4.8 MB (unchanged)
NotoColorEmoji.ttf 111 MB ← Apple emoji 🍎
NotoSans-Regular.ttf (unchanged)
NotoNaskhArabic-*.ttf (unchanged)
SysFont-Regular.ttf 25 MB ← SF Pro added
SF-Arabic.ttf 837 KB ← SF Arabic added

The rule

/data/adb/modules/AppleFonts/
  system/
    fonts/
      NotoColorEmoji.ttf← appears at /system/fonts/NotoColorEmoji.ttf
      SysFont-Regular.ttf← appears at /system/fonts/SysFont-Regular.ttf
      SF-Arabic.ttf← appears at /system/fonts/SF-Arabic.ttf
    etc/
      fonts_customization.xml← overlays /system/etc/fonts_customization.xml
The rule

Whatever you put in system/ inside your module directory gets overlaid on the real /system at the matching path. Files not in your module remain visible from the real partition.

06

post-fs-data.sh — The Heart

Reading config with no jq

jq doesn't exist on Android's minimal shell. We parse JSON with grep -o:

# grep -o extracts matching text only
_W=$(grep -o '"wght":[0-9]*' "$CONFIG" | grep -o '[0-9]*$')
[ -n "$_W" ] && WGHT=$_W

# Pattern '"wght":[0-9]*' matches: "wght":300
# Second grep extracts just the number: 300

Toggling fonts — the filesystem is the switch

if [ "$EMOJI" = "false" ]; then
  # Move Apple emoji OUT of magic-mount → stock Noto becomes visible
  [ -f "$FONTS/NotoColorEmoji.ttf" ] && mv "$FONTS/NotoColorEmoji.ttf" "$STORE/"
else
  # Move Apple emoji BACK IN → KSU overlays it again
  [ -f "$STORE/NotoColorEmoji.ttf" ] && mv "$STORE/NotoColorEmoji.ttf" "$FONTS/"
fi
Elegant design

No separate "disable flag" config needed at the overlay level. The presence or absence of the file in the module directory IS the toggle. Move it out = disabled. Move it in = enabled.

Rewriting fonts.xml with awk

We need to find the <family name="sans-serif"> block, replace it with SF Pro, and output the whole 1700+ line file. awk does this in one command with no external dependencies:

awk -v do_latin="$LATIN" -v wght="$WGHT" '
  { lines[NR] = $0 }          # PASS 1: store every line

  END {
    # PASS 2: find sans-serif block boundaries
    for (i = 1; i <= NR; i++) {
      if (lines[i] ~ /name="sans-serif"/) {
        # scan backward for <family
        for (j = i; j >= 1; j--)
          if (lines[j] ~ /<family/) { ss = j; break }
        # scan forward for </family>
        for (k = i; k <= NR; k++)
          if (lines[k] ~ /<\/family>/) { se = k; break }
      }
    }
    # Replace lines ss..se with SF Pro block, print rest unchanged
    for (i = 1; i <= NR; i++) {
      if (i == ss)  print sf_pro_block
      if (i >= ss && i <= se) continue
      print lines[i]
    }
  }
' /system/etc/fonts.xml > "$MOD_XML"

This is the two-pass awk pattern: read everything into memory in the main block, do complex multi-line analysis in the END block. Standard technique for XML-like transformations in shell.

07

Binary Patching Font Weight

SF Pro is a variable font — one file that contains all weights (Thin to Black). The fvar OpenType table stores the default axis values. We surgically edit those 4 bytes at boot.

OpenType Fixed 16.16 format

WeightDecimalHexFixed 16.16 bytes
Thin (100)1000x006400 64 00 00
Light (300)3000x012C01 2C 00 00
Regular (400)4000x019001 90 00 00
Bold (700)7000x02BC02 BC 00 00

The patch process

# Step 1: Read font header — how many tables?
N=$(_hex2dec "$(_rbytes "$FONT" 4 2)")

# Step 2: Scan table directory for "fvar" tag (hex: 66766172)
while [ "$i" -lt "$N" ]; do
  BASE=$((12 + i * 16))
  if [ "$(_rbytes "$FONT" "$BASE" 4)" = "66766172" ]; then
    FVAR_OFF=$(_hex2dec "$(_rbytes "$FONT" $((BASE+8)) 4)")
    break
  fi
  i=$((i + 1))
done

# Step 3: Inside fvar, find "wght" axis (hex: 77676874)
# Step 4: At offset +8 write new Fixed 16.16 value
printf '\x01\x2c\x00\x00' | dd of="$FONT" bs=1 seek=$DEF_OFF count=4 conv=notrunc
Why dd and od?

These are the only byte-level I/O tools guaranteed on Android's minimal shell. od -An -tx1 prints bytes as hex pairs. dd bs=1 skip=N count=4 reads 4 bytes from an offset. No Python, no xxd needed.

08

The Emoji Bug — A Debugging Story

This is the real story. Understanding bugs is as important as writing features.

v1.0.0 — First attempt
Shipped emoji as NotoColorEmoji.ttf. User reported Android emoji still showing.
❌ Wrong theory: assumed com.android.i18n APEX was shadowing our file.
v1.2.0 — Wrong fix
Renamed to AppleColorEmoji.ttf, injected into fonts.xml
❌ fonts.xml is DEPRECATED. Minikin reads font_fallback.xml which only references NotoColorEmoji.ttf. Stock Noto won every time.
v1.3.0 — Correct fix
Name Apple emoji NotoColorEmoji.ttf. Magic-mount delivers it to font_fallback.xml's reference.
✓ User reports: "it works"

The APEX dead-end

# We checked the actual device:
$ find /apex/com.android.i18n -name "*.ttf"
(no output — no emoji fonts in APEX at all)

$ ls /apex/com.android.i18n/etc/
icu/  (only ICU locale data — no fonts)
Lesson

Our APEX theory was based on older Android documentation where APEX did contain emoji. Android 16 reorganized this. Don't trust assumptions — check the actual device with adb shell ls and find.

The emoji size bug

After fixing the naming, emoji were showing as Apple but appeared smaller than stock Noto. Root cause: the glyph advance width in the 111MB file was 2048 units (1.0× em) vs 2400 units (1.17× em) needed to match the reference file. We patched all hmtx advance widths + OS/2 + hhea metrics to fix the proportions.

OEM Compatibility

Samsung, Xiaomi, and other OEMs customize the font system heavily. Here's how we handle it.

OEMDefault fontOur fix
Stock AOSPRobotofonts_customization.xml replaces sans-serif
Samsung One UISamsungSansAuto-detected, SF Pro copied under OEM filename
Xiaomi MIUI/HyperOSMiSansAuto-detected, same approach
OnePlus OxygenOSOnePlus Slate / SysFontPrimary dev device — natively supported

Alias detection in customize.sh

# Parse the device's own fonts.xml to find OEM font filenames
awk '
  /name="sans-serif"/ { in_ss=1 }
  in_ss && /style="normal"/ {
    if (match($0, />[A-Za-z0-9._-]+\.ttf/))
      print substr($0, RSTART+1, RLENGTH-1)  # extract filename
  }
  in_ss && /<\/family>/ { in_ss=0; exit }
' /system/etc/fonts.xml | while read OEM_FONT; do
  case "$OEM_FONT" in
    SysFont*|Roboto*|NotoColor*|SF-*) continue ;;  # skip our own
  esac
  # On Samsung: creates SamsungSans-Regular.ttf → SF Pro
  cp "$FONTS/SysFont-Regular.ttf" "$FONTS/$OEM_FONT"
done

The WebUI

KernelSU has a built-in WebView that serves files from the module's webroot/ directory. No app installation required.

User moves weight slider in browser
WebUI JavaScript POSTs to KSU API
fetch('/api', { method: 'POST', body: JSON.stringify({wght: 300}) })
KSU WebView executes scripts/apply.sh
apply.sh writes /data/adb/AppleFonts/config.json
Next reboot → post-fs-data.sh reads config.json → applies settings
Why reboot required?

Font changes happen at the Zygote level — the parent process all apps fork from. Changing fonts requires restarting every app. The only practical way is a full reboot.

// config.json
{
  "wght": 300,     // font weight 100-1000
  "latin": true,   // SF Pro enabled
  "arabic": true,  // SF Arabic enabled
  "geeza": false,  // Geeza Pro
  "cocon": false,  // Cocon Next Arabic
  "emoji": true    // Apple emoji
}
11

Lessons Learned

1
"Deprecated" warnings are literal
fonts.xml says "DEPRECATED" at the top. We assumed that meant "deprecated for apps." It means "deprecated as a system font config source." Minikin uses font_fallback.xml now. Always read warnings at face value.
2
Debug with the real device, not assumptions
We theorized about APEX shadowing for days. The device had no APEX emoji at all. The right approach: adb shell → ls, find, cat → see what's actually there.
3
Check file permissions in debug scripts
font_fallback.xml is root-only readable. Our debug script ran as ADB shell (non-root) and couldn't see it. Key diagnostic files require root access. Always su -c your debug scripts.
4
File format matters as much as file name
We worried about filenames (AppleColorEmoji vs NotoColorEmoji). The real issue was that the file we thought was Apple emoji was actually Google Noto renamed. Always verify file content, not just name.
5
post-fs-data timing is everything
The entire module depends on running code after /data is mounted but before Zygote starts. Use service.sh for anything that can wait until after boot.
6
Android shell is not Linux shell
No jq → use grep/awk. No python3 → use dd/od for binary math. /bin/sh might be toybox, mksh, or busybox. Test for portability, not comfort.
7
The boot watchdog is non-negotiable
A buggy module can cause a permanent bootloop. The 90-second self-disable in service.sh saves users from having to manually disable via recovery. Always include this in any boot-critical module.
